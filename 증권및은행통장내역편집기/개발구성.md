## 사전 파일을 .js 로 둔 이유
`index.html`을 더블클릭(file://)으로 열면 브라우저가 같은 폴더의 .json 을 fetch로 읽지 못한다. 그래서 내용은 순수 JSON 그대로 두고 `<script>`로 읽히도록 감쌌다. 4단계 "사전 반영"은 이 파일을 다시 쓴다.

## 처리 흐름 (engine.js)
1. `readWorkbook` — 앞부분이 `<`로 시작하면 HTML로 보고 meta charset(EUC-KR 등)으로 해독해서 읽는다(NH투자증권 .xls가 실제로는 HTML). 그 외는 SheetJS `cellDates:true`.
2. `parseFileName` — `번호_약칭(계좌번호)_문서종류` 해석. 괄호가 없으면 `번호_기관_…`.
3. `resolveAbbreviation` — 약칭 표(사전 abbreviations)로 은행명/증권사명 후보. 이름에 은행·증권이 들어 있으면 그쪽만 남김.
4. `detectLayout`
   - 앞 15열 중 날짜 칸이 가장 많은 열 = 날짜 열. (엑셀 일련번호 숫자는 금액과 구분 불가라 날짜로 보지 않음. 실제 날짜 셀은 SheetJS가 Date로 줌)
   - 날짜 행 간격의 최빈값 = 거래 1건의 줄 수.
   - 첫 날짜 행 위(빈 줄은 건너뜀)로 올라가며, 날짜가 없고 숫자 칸이 1개 이하인 줄을 헤더 묶음으로 모음. 빈 줄·날짜 줄·숫자 많은 줄(한화 요약 줄)에서 멈춤.
   - 묶음 중 채워진 칸이 최다의 40% 이상(최소 2) = 헤더 줄. 첫 헤더 줄 위의 듬성한 줄 = 제목 줄. 헤더 아래 듬성한 줄 = 줄바꿈된 헤더로 보고 바로 위 헤더 칸에 이어 붙임(신한 `예탁금`+`이용료`).
   - 헤더 줄 수 ≠ 거래 줄 수면 경고 후 거래 줄 수에 맞춤.
   - 거래는 날짜 행을 기준으로 N줄씩 묶어 한 줄로 평탄화. 어디에도 묶이지 않은 줄은 `skippedRows`로 알림(조용히 버리지 않음).
5. 은행/증권 판별
   - 은행형: 입금·출금(또는 부호 있는 거래금액)·잔액 열이 있고, `예수금` 열이 없고, 증권사 프로필에 안 맞음.
   - 증권형: 증권사 프로필 점수 통과(기존 BrokerAutoMapper.detect 규칙 그대로) 또는 거래종류+거래금액+예수금류 열 존재.
   - 기존 도구는 사전 별칭이 정식 명칭뿐이라 파일명 가산점이 거의 작동하지 않았다 → 약칭을 정식 명칭으로 바꾼 뒤 점수 계산에 넣어 해결(사전 원본은 수정하지 않음).
6. 상태
   - ready(자동 완료): 기관 판별, 구조 경고 없음, (증권은) 사전 프로필 일치
   - review(확인 필요): 사전에 형식 없음, 이름 불일치, 잔고증명, 숫자로 못 읽은 금액, 구조 경고
   - nocash(현금거래 없음): 증권형에서 거래금액·잔액이 모두 0/빈칸
   - fail(실패): 읽기 실패, 날짜 열·헤더 없음, 거래 0건
   - 금액을 숫자로 못 읽으면 null로 두고 알린다(0으로 바꾸지 않음).

## 변환 흐름 (convert.js)
- 계좌명: 파일명(확장자 제외). 같은 파일에 시트가 여러 개면 "파일명 시트명". 계좌번호는 선택.
- 날짜 순서: 첫 날짜 > 마지막 날짜면 뒤집음(두 기존 도구와 같은 규칙). 편집에서 반대로 뒤집기 가능.
- 레거시 엔진 입력 전 Date 셀을 'YYYY-MM-DD' 글자로 바꿈 — 기존 _parseDate 는 Date 객체를 못 읽음.
- 은행형: 입금·출금(또는 ± 거래금액) → 잔액 재계산. 기초잔액 = 첫 행 원본잔액 − 입금 + 출금. 적요 = 선택한 열 값을 " / "로 합치고 같은 값은 한 번만, 제외 값 적용. 금액을 숫자로 못 읽으면 0으로 계산하되 행 번호와 함께 알림.
- 증권형(기존 도구 순서 그대로): buildPhase3Config(사전 판별·열 매핑, 사용자 열 지정 덮어씀) → preprocessData ×2(2·3단계) → transformPhase3(적요 "결과 생성" 열) → buildAutoClassifyConfig + autoDistributePhase5(기존 "잔액 기준 자동 분류" 버튼을 자동 실행) → transformPhase4(제거 분리) → transformPhase5 → verifyPhase5.
  - 기초잔액: 기존 도구는 사용자가 입력(기본 0). 새 도구는 제거 대상이 아닌 첫 기준점의 원본잔액 − 계산 증감으로 역산하고, 1차 분류 후 역산값으로 한 번 더 자동 분류. 직접 입력 가능.
  - 수수료·제세금: 기존 규칙(비용 열이 있으면 별도 행 강제) 유지. 계좌별로 "거래금액에 포함" 선택 가능.
- 입출금외 내역: 제거 항목·미분류 거래종류·금액 0 행을 사유와 함께 보관. 수량 × 단가 금액을 계산해 적요 끝에 "897,000원" 형태로 붙임. 현금거래 없는 계좌(IBK 등)도 변환을 돌려 이 내역을 남김.
- 상태: 잔액 불일치(mismatch) > 확인 필요(review: 판별 단계 경고·변환 알림) > 자동 완료(ready). 결과 행 0 = 현금거래 없음(nocash).
- 다운로드(통장변환결과_YYYYMMDD_HHMM.xlsx): 요약 → 입출금외내역(전 계좌) → 계좌별 결과 시트(계좌명, 31자·특수문자 정리, 중복 시 (2)) → [선택] 원본_계좌명 시트. 숫자 서식 #,##0.

## 사전 반영 (dictionary.js, 4단계)
- 배포 구조: GitHub Pages 정적 페이지라 브라우저가 저장소 파일을 직접 고칠 수 없다. 반영은 메모리의 window.BANKBOOK_DICTIONARY 에만 하고, "사전 파일 저장"으로 institutions.js 를 내려받아 관리자가 커밋한다. "사전 불러오기"로 받은 파일을 시험 적용(새로고침 시 배포본으로 복귀).
- 저장 내용(기관 단위만): 증권 — 열 이름 프로필(columns), 입금/출금/제거 거래종류, 수수료 포함 여부(inferredFeeMode, 새 필드), 열이 5개 미만이면 minMatchedKeys. 은행 — 열 이름, 적요 열(memoCols), 적요 제외 값(excludedMemoValues). 공통 — 파일명 약칭. 변경 때마다 version +1, changelog 기록.
- 증권 프로필 병합: 같은 증권사에서 열 이름이 같은 프로필이 있으면 갱신, 없으면 추가. 거래종류는 이번 계좌에 나온 것만 다시 배정하고 다른 계좌에서 배운 값은 유지.
- 반영 후: 직접 편집하지 않은 계좌(edited=false)와 반영한 계좌를 새 사전으로 다시 판별·변환(계좌명·저장 여부 유지). 원본 행은 계좌 객체에 비열거 속성(rows)으로 보관.
- 적용: 은행 프로필 열 이름을 일반 규칙보다 우선. 프로필에 적요 열이 여러 개면 모두 기본 선택. 증권 프로필의 inferredFeeMode 는 자동 분류 결과보다 우선(사용자 편집 > 사전 > 자동).
- 저장하지 않은 사전 변경이 있으면 창을 닫을 때 브라우저 경고.

## 개선 1단계 (2026-11-10): 보수적 판별 · 검증 강도 · 확인 완료 · 기초잔액
### 증권사 판별 (engine.js decideBroker, 사용자 규칙 16)
- 파일명 기관: "번호_약칭(계좌)" 약칭 → 없으면 파일명 단어 앞부분 약칭(예: "키움해외"→키움). 서로 다른 후보가 여러 개면 확정 안 함. "해외/외화" 단어는 외화 힌트.
- 파일명에 증권사가 있으면 그 증권사 형식 안에서만 선택: 모든 열 일치 → 확정 / 필수 4열 + 최소 열 수 일치 → 확정하되 "일부 열 다름" 확인 필요 / 그 외 → 기관만 두고 형식 미확인(열 직접 지정). 다른 증권사 형식과 완전히 같으면 충돌 안내(확인 필요), 그래도 파일명을 따름.
- 파일명에 증권사가 없으면: 모든 열이 일치하는 증권사가 딱 한 곳일 때만 확정. 부분 일치(9/10 등)는 절대 자동 확정 안 함.
- 형식 지문(signature): 사전 반영 때 그 파일의 전체 열 이름을 함께 저장, 지문의 90% 이상이 있어야 완전 일치. 흔한 열 이름만으로 반영된 형식(예: IM 6열)이 다른 증권사(대신) 파일과 혼동되던 문제를 막음. 기존 사전 형식은 지문이 없어 기존 동작 유지.
- 열 이름 비교 시 앞 따옴표(' ‘ ’ ` ") 무시.
- 은행: 파일명에 은행이 없으면 열 구조가 사전 은행 형식과 같아도 은행명을 자동으로 넣지 않음(안내만).
- 기존 엔진의 점수 판별(buildPhase3Config) 대신 위 결과로 phase3 설정을 구성(필드 형식은 동일). 샘플 변환 결과 불변 확인.
- 판별 근거(basis)를 화면·요약 시트에 표시.
### 자동 완료 기준 (convert.js)
- 증권 확인 필요 사유: ① 잔액으로 추정한 분류가 있는데 독립 기준점(기초잔액 계산에 쓴 기준점 제외)이 없음 ② 기초잔액 음수 ③ 사전과 다르게 분류 ④ 사전에 없고 잔액으로도 확인 안 된 분류 ⑤ 사전에 없는데 금액 있는 거래를 제거로 추정. 사전으로 정해진 분류뿐이면 거래 1건이어도 자동 완료(틀릴 곳이 없음).
- 금액 있는 거래를 추정으로 전부 제거해 결과가 0행이면 "현금거래 없음"이 아니라 확인 필요.
- 은행: 입금·출금이 열로 정해져 추정이 없으므로 기준점 수는 참고 정보로만.
- 판별 단계 사유(reviewReasons): 기관 미확정, 사전 형식 없음/일부 다름, 다른 증권사 형식과도 일치, 해외 표시, 숫자 못 읽음, 잔고증명, 계좌번호 불일치 등.
### 확인 완료
- '사용자 확인' 상태. 잔액 일치면 메모 선택, 불일치·변환 전이면 사유 필수. 자동 판정(autoStatus)은 보존. 다시 편집·자동분류·사전 반영 재판별 시 해제. 요약 시트에 상태·자동 판정·확인 사유·확인 메모·판별 근거 열.
### 기초잔액
- 입력하면 독립 기준점이 1개 늘어 첫 거래부터 검증. 증권은 분류를 직접 고치지 않았다면 그 값으로 자동 분류 다시. 기준점 부족 계좌는 입력란 강조.
- 실험 근거: 신한 잔액 희소·사전 분류 없음 → 이전 "자동 완료"(기초 −65,533,495) → 이제 확인 필요. 키움(거래 1건) 기초잔액 입력 → 독립 기준점 0→1, 1,000원 틀리게 넣으면 잔액 불일치.

## 개선 2단계 (2026-11-10): 증권사별 처리 방식 사전 구조 (사용자 규칙 15)
### 사전 구조 2 (schemaVersion: 2, 내용 개정은 version)
```
securities.keywordRules            공통 키워드(기존 엔진 고정값을 옮김): directionHints{deposit,withdrawal}, removalHints, blockDeposit, mirrorPatterns
securities.domestic[] / foreign[]  국내·해외 별도 목록 (같은 증권사·같은 열 이름이라도 해외 계좌는 해외 목록만 사용)
  { id, name, aliases,
    shared: {depositTypes, withdrawalTypes, removalTypes}   증권사 공통 분류 — 형식이 달라도 같은 증권사면 사용
    specialRules?                                           증권사 단위 처리 규칙(모든 형식에 적용, 형식에 자기 규칙이 있으면 형식 우선)
    keywordRules?                                           증권사 전용 키워드(공통 키워드를 항목별로 덮어씀)
    profiles: [{ columns, signature?, depositTypes, withdrawalTypes, removalTypes, specialRules?, inferredFeeMode?, minMatchedKeys? }] }
```
- 처리 방식 결정(engine.js brokerProcessing): 형식 분류(우선) + 증권사 공통 분류(형식에 없는 거래종류만 추가) + 특수 규칙(형식 > 증권사) + 키워드(증권사 > 공통 > 기존 엔진 값). 형식이 확정되지 않아도 파일명으로 증권사를 알면 공통 분류·증권사 규칙을 쓴다. 간편 형식(classificationKeywords, 포함 검색)에는 공통 분류를 섞지 않는다.
- 분류 우선순위: 기존 엔진(buildAutoClassifyConfig)과 같이 제거 > 입금 > 출금. 한 형식 안에서 두 칸에 있으면 사전 검사가 경고(유진 "공모불입(현금)" — 기존 도구 사전에서 온 값, 제거로 적용).
- 국내/해외 선택(engine.js chooseMarket): 파일명 해외/외화 → 해외 목록만(맞는 형식이 없으면 국내 형식으로 대신하지 않고 확정 보류). 그 외 → 국내 우선, 국내 미확정이고 해외 형식과만 모든 열 일치하면 해외. 해외 계좌는 "해외 계좌(원화·외화 구분 확인)" 사유로 확인 필요(통화 분리는 3단계).
- 대신 규칙: 기존 엔진은 id==='daishin' 일 때만 행 제외·금액 대체를 했다. convert.js preprocessByRules 가 규칙(ignoreTradeTypeContains·amountOverrideByTradeType)만 보고 적용 → id 와 무관, 다른 증권사에도 사전으로 줄 수 있음. 구조 변환 때 대신의 두 형식 공통 규칙을 증권사 단위로 올림.
- 키워드 적용(convert.js applyKeywordRules): securities-legacy.js 는 고치지 않고, 변환 직전에 DataTransformer 의 키워드 목록·방향 추정 함수를 사전 값으로 바꿔 끼운다. 사전에 없는 항목은 처음 읽은 기존 값으로 되돌린다. _summarizeTypeResiduals 안의 지역 목록은 바꿀 수 없음(기존 값 고정).
- 사전 반영(dictionary.js applySecurities): 계좌의 국내/해외(marketOf)에 맞는 목록에 기록, 형식 분류와 함께 증권사 공통 분류도 갱신(다른 칸에 있던 값은 옮기고 changelog 에 표시).
- 구조 변환(migrate 1→2): keywordRules 추가, 형식끼리 엇갈리지 않는 분류만 shared 로(국내 103·해외 8개), 모든 형식에 같은 특수 규칙이면 증권사 단위로. 불러올 때 자동 변환, 저장하면 구조 2로 저장.
- 안전장치: parse = JSON 문법 → 구조 변환 → 검사(validate). 오류(구조·id/이름 중복·목록 형식·더 새로운 구조)면 거부하고 지금 사전 유지. 경고(필수 열 없는 형식, 중복 분류, 모르는 특수 규칙, 사전에 없는 약칭 대상)는 안내만. 배포 사전이 깨지면 빈 사전(emptyDictionary)으로 동작 + 빨간 안내.
- 기준값 변화: 키움해외 CSV 만 review(0행) → mismatch(41행). 해외 키움 형식으로 판별·변환되지만 원화·외화가 한 잔액 열에 섞여 불일치 — 3단계에서 통화 분리 후 갱신. 나머지 샘플 결과 불변(공통 분류는 샘플 형식이 모두 사전에 있어 쓰이지 않음 — 새 형식에서 쓰임, run-structure 로 확인).

## 개선 3단계 (2026-11-10): 외화 분리
- 통화별 분리(engine.js splitByCurrency, analyzeFile 에서 시트마다 실행): 사전 형식(또는 증권사)의 currencySplit 이 있고 통화 열에 2개 이상 통화가 있을 때만 나눈다. 설정이 없으면 나누지 않고 "통화 혼재(분리 안 됨)" 확인 필요(추측 금지).
  - 외화 쪽 열 = 형식 열 + currencySplit.foreign.columns(정산금액 등). 원화 쪽 열 = 형식의 비금액 열(일자·거래종류·종목 등) + currencySplit.base.columns(금액·잔액). 금액 열(MONEY_KEYS)은 원화 쪽에 섞지 않는다.
  - 행 배정: 그 통화 행 + 원화 쪽은 원화 금액이 있는 외화 행(환전) → 환전 행은 두 계좌 모두. 외화가 하나면 외화 금액이 있는 원화 행도 외화 계좌에.
  - 원화 쪽 분류 = currencySplit.base 의 목록(외화 기준 공통 분류는 섞지 않음 — 외화매도는 외화 출금이지만 원화 입금).
  - 계좌명 끝에 [통화]. 판별 단계 상태는 해외/파일명 사유를 지우고 다시 계산(최종 상태는 변환 검증으로).
- 숨은 비용(convert.js addHiddenCostColumn): settlementCol 이 있으면 "기타비용" 열을 만들어 빈 extraCostCol 에 연결 → 기존 엔진이 "(기타비용)" 출금 행으로 낸다. 매수/매도 두 식 중 0 이상·작은 값, 금액의 1% 초과는 무시. 같은 날·같은 거래종류에 정산금액 0 인 행이 있으면 묶음 합계로 계산(합산 정산).
- 하루 단위 검증·통화별 허용오차(convert.js): 기존 엔진의 날짜별 마지막 기준점(_summarizePhase5MismatchDates)으로 판정. 허용오차 원화 1·외화 0.01. 같은 날 안에서만 생긴 차이는 안내(notes)만. 기말 잔액 표시는 기존과 같이 원본 잔액이 있는 마지막 행 기준(v.calculated/v.original).
- 잔액 보정(선택, config.balanceAdjustment): 기존 엔진의 mismatch_dates 방식으로 날짜별 "(잔액보정)" 행. 넣으면 확인 필요 + 사유. 기존 엔진 규칙상 잔액 0 + 금액 있는 행은 기준점이 아니라 그 날 누락분은 다음 기준점에서 보정됨.
- 안내와 문제 구분: output.notes(상태에 영향 없음 — 숨은 비용·합산 정산·공통 분류 적용·중간 차이·누락 가능성) / output.issues(확인 필요).
- 사전 반영(dictionary.js applyCurrencySide): 통화별 계좌는 나눈 기준 형식 안에 기록(원화 → currencySplit.base, 외화 → 형식 분류, 정산금액 열 → currencySplit.foreign). 새 형식을 만들지 않는다. 검사(validate)가 currencySplit 구조를 확인.
- 다시 판별(convert.js rebuildAccounts): 같은 통화 계좌가 id·이름을 이어받고 다른 통화 계좌는 새로 생성. 화면(rebuildAfterDictionaryChange)은 같은 원본의 형제 계좌를 한 번만 다시 만든다.
- 첫 사례: 키움해외 CSV — USD 자동 완료(숨은 비용 5건 5.01), KRW 원본 입금 누락으로 잔액 불일치. 기록: cases/20261110_키움해외_요약.txt(로컬).

## 예외 규칙 (2026-11-10, 작업 20261110-017)
- 사용자 지시: 키움해외처럼 한 건에서만 나온 규칙은 예외로 분류. 같은 카테고리 = 열 이름이 모두 같을 때. 그 경우 같은 거래종류도 입금/출금이 될 수 있으므로 잔액 기준으로 분류.
- 사전: 증권사 항목의 exceptions[] = { id, label, cases, source, signature(전체 열 이름), classificationBasis: "balance", currencySplit? }. 키움 해외: 형식1의 currencySplit 을 예외 kiwoom-foreign-krw-usd-csv 로 이동(열 27개), 원화 쪽 고정 분류 목록 삭제(사전 버전 4). 형식1 자체는 기존 도구 사전 그대로(오타만 수정).
- 판별(engine.js findException·sameHeaderSet): 판별된 증권사의 예외 중 signature 와 파일 열 이름 집합(따옴표 무시)이 완전히 같은 것만. 판별 근거·안내에 "예외 규칙 …(사례 N건)" 표시. 통화 분리는 예외의 currencySplit 이 우선.
- 분류(engine.js brokerProcessing balanceBasis, convert.js): 사전 분류·공통 분류를 쓰지 않고 기존 자동 분류 후 "행별 잔액 근거"로 확정 — 원본 잔액이 있는 연속 행에서 잔액 변화가 +금액(−비용)이면 입금, −(금액+비용)이면 출금, 한 방향만 맞는 경우만 근거. 근거가 한 방향인 거래종류는 그 방향으로 바로잡음(키움해외 USD 외화매도: 기존 자동 분류는 "매도" 키워드로 입금 → 잔액 근거로 출금).
- 모든 증권 계좌 공통 안전장치: 같은 거래종류가 잔액상 입금·출금 양쪽 근거를 가지면 확인 필요 사유. 근거는 output.evidence 로 남김(추후 근거 표시용).
- 사전 반영: 예외(잔액 기준) 계좌는 분류를 저장하지 않고 안내(applySecurities 에서 거부). 검사(validate)가 exceptions 구조(id, signature 3개 이상, classificationBasis, currencySplit, cases)를 확인.

## 개선 4단계 (2026-11-10): 순서가 섞인 파일 자동 복원
- 실험(샘플 순서를 메모리에서 섞음): 날짜순 정렬만으로는 거의 효과 없음(뒤집힌 구간은 같은 날 안 순서도 뒤집혀 그 날 마지막 잔액이 바뀜).
- 방법(convert.js repairOrder, 분류 없이 "|잔액 변화| = 금액(±비용, 정산금액)"만 사용): ① 날짜순(같은 날은 원래 순서) ② 날마다 그대로/뒤집기 중 잔액이 더 잘 이어지는 쪽 ③ 그래도 끊기는 날은 전날 마지막 잔액에서 이어지는 행을 하나씩 붙임(그 날 모든 행에 잔액이 있고 60행 이하, 다 이어질 때만). 잔액 0 + 금액 있는 행은 잔액 없음으로 봄.

- 결과: 샘플 29개 계좌 결과 앞부분 일치 이전과 동일, 40_한화 올바름(수수료 출금, 기말 220). tests/run-prefix.js(9항목).

## 기존 증권 도구 분석 (reference/stockbalance/index.html)
같은 이름의 함수가 여러 번 정의되어 있으며, **나중 정의가 실제로 실행된다.**

- 실제 단계 순서: upload → phase1(행 병합) → phase2(통화 분리) → phase3(열 매핑) → phase5(분류·검증) → download. phase4 화면은 순서에서 빠져 있다(2377행).
- 엔진으로 가져올 부분 (최종본 기준 행 번호)
  - 기관 사전과 판별: `BrokerAutoMapper` 2411–2765 (presets 국내 37곳, foreignPresets, detect, 대신·KB 전처리)
  - 기본 도구: `DataTransformer._parseDate` 1892, `_formatDate` 1923, `autoSortByDate` 1931, `transformPhase1` 1957, `transformPhase2` 1958, `_getExtraCostDetails` 2068, `_getRowValues` 2083
  - 분류·검증 최종본: 2915–4445 (`transformPhase4` 3139 = 제거 행 분리, `_buildPhase5Projection` 3175, `transformPhase5` 3354, `verifyPhase5` 3494, `autoDistributePhase5` 4332 = 잔액 기반 자동 분류)
  - 완료 처리 최종본: `AppController.processPhase5` 4646
- 여러 번 정의된 함수(앞쪽 정의는 사용되지 않음): transformPhase5(2039, 2300 → 3354), verifyPhase5(2038 → 3494), autoDistributePhase5(2203, 2961 → 4332), classifyByBalance(1961 → 2226), handlePhase5AutoClassify(6곳 → 4468), renderPhase5View(4곳 → 4531), processPhase3(3곳 → 2811), processPhase5(1367 → 4646), handleDownload(1416 → 4608) 등.
- 행 병합 가정: "선택한 헤더 행 수 = 거래 1건의 줄 수". 신한처럼 헤더 줄바꿈이 있으면 맞지 않는다.

## 알려진 문제 / 다음 작업
- 현대차 파일은 거래 1건뿐이라 거래 줄 수(3)는 헤더 구조로 추정한 값.
- KB국민은행 시트 2개는 계좌번호가 없어 "파일명 시트명"(…_10월 KB1, …_10월 KB2)으로 구분(사용자 확인: 계좌번호 불필요, 2026-11-10).
- iM증권은 배포 사전에 아직 프로필이 없음 — 화면에서 열 지정 후 "사전에 반영 → 사전 파일 저장"으로 추가 가능(테스트로 확인). 배포 사전에는 아직 넣지 않음(사용자 확인 후).
- 편집 내용은 새로고침하면 사라짐 — 팀 공유(GitHub) 구조상 정상(사용자 확인 2026-11-10). 기관 단위 설정은 사전 반영으로 유지.
- 외화 분리는 3단계 완료. 통화 분리 설정은 키움 해외 예외 규칙(사례 1건)에만 있음 — 다른 증권사 해외 파일은 사례가 들어오면 예외 규칙으로 기록.
- 은행형 변환은 하루 단위 검증·잔액 보정 옵션이 아직 없음(증권형만).
- tools/extract-presets.js --force 로 다시 만들면 구조 1 사전이 생김 → `node tools/check-dictionary.js --migrate` 로 구조 2 저장(불러올 때도 자동 변환됨).
- 입출금외 내역의 "주식매도입금"(미래)처럼 요약 행이 제거된 경우도 같은 시트에 남는다(사유: 제거 항목).
